# Отладка зависания в меню при простое (r0.282 → r0.288)

Симптом: включил прошивку, не нажимаешь ничего — питание/экран/меню живы, но
иногда через ~5–10 минут система зависает (не отвечает на кнопки/тач).
Проявлялось на r0.277–r0.281; причина пока не найдена.

## Статус (r0.288)

- Heartbeat `MHB` из r0.282 **убран** как временный мусор (по запросу чистки).
- При повторном тесте вернуть его одной строкой в menu.c, цикл меню
  (после `udelay(16000)`): `{ static unsigned mhb=0; if ((++mhb%300)==0) printf("MHB %u\n", mhb); }`

## Как воспроизводить и что прислать

1. Прошить r0.282, держать подключённым UART (115200).
2. Включить и НЕ нажимать ничего 10–15 минут.
3. Если зависнет — прислать **хвост UART-лога** (последние 30–50 строк).

По хвосту определяем:
- `MHB` оборвался → core0 застрял после последнего номера (видно, на какой
  итерации ~5-секундного окна);
- экран залит `TCH: ...` → спам тач-панели (шум GT911 без касаний);
- строка `P: <addr>` → prefetch/data abort с адресом;
- если `MHB` идёт дальше, а система «мертва» — виснет CPU1 (TFT) или
  вызов внутри `usb_input_poll` (OHCI/клад/пад), куда core0 не возвращается.

## Подозреваемые (код-ревью r0.282)

- Опро неблокирующий: `usb_kbd_poll`/`kbd_read_report` идут с таймаутами
  (usb_ohci.c имеет таймауты, бесконечных циклов нет).
- В меню есть печать `TCH:` при каждом изменении g_ts_seq (шум тача давал бы
  непрерывный спам UART) — проверяется по логу.
- CPU1 (TFT-рендер) и гонка за PA_DAT с тачем/падом — потенциальный источник.

## Когда уберём heartbeat

После того как причина найдена и исправлена (или если зависание не
воспроизведётся) — удалить блок `MHB` из menu.c и поднять версию.
