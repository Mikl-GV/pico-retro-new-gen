# Диски PC/XT-286 (pxt): проблемы записи и медленного чтения

Статус: **диагноз готов, реализация отложена владельцем** (отдельная задача).
Актуально на r1484. Связанные документы: `docs/AUDIT_MS1504_PXT.md` (PX-07, PX-09),
`docs/MEMORY.md`, `docs/PITFALLS.md`.

## 1. Симптомы со стенда (r1484)

- C: открывается, файлы видны, но при попытке открыть/изменить файл DOS пишет
  «запись невозможна».
- B: и D: недоступны (D: при этом виден в логе как смонтированный stream-образ).
- Чтения с HDD идут рывками: в логе `slow d=2 ... us=247890`, `us=459528`,
  `us=251525` — 250–460 мс на один запрос.
- Звук к этой задаче не относится (см. `AUDIT_MS1504_PXT.md`, PX-08/MS-02).

## 2. Что именно в коде

| Место | Факт |
|---|---|
| `pxt/src/emulator/disks-h3.c.inl:108-117` | `pxt_disk_set_stream(drive, cb, len)` — только колбэк **чтения**, `readonly = 1` |
| `disks-h3.c.inl:249` | `bios_write`: `if (disk[drivenum].readonly \|\| !disk[drivenum].base)` → отказ (AH=…) |
| `disks-h3.c.inl:37-38` | у диска есть `inserted` и `readonly`, поля `write_cb` нет вовсе |
| `h3_bare/cores/fat.h:46,54-56` | запись только последовательная: `fat_write_file`, `fat_write_begin/data/end`; **записи по смещению нет** |
| `h3_bare/cores/fat.h:40` | чтение по смещению есть — `fat_stream_read(s, offset, buf, len)` |
| `pxt_host.c:546,586` | `emu_run_pxt()` ставит только A: (`pxt_disk_clear(0); pxt_disk_set(0, …)`); B:/C:/D: приходят извне |

## 3. Почему в эталоне работает

`emulator-refs/pico-286/src/emulator/disks-rp2350.c.inl` использует FATFS:

- `:40` — `f_open(&file, pathname, FA_READ | FA_WRITE)`;
- `:156-162` — `f_lseek` + `f_read` на чтении сектора;
- `:256-269` — `f_lseek` + `f_write` на записи сектора.

То есть запись у эталона есть на уровне файловой системы: образ открыт на запись,
позиция задаётся `f_lseek`, пишутся те же 512 байт. У нас порт заменил FATFS на
собственный FAT-слой (`fat.c`), у которого нет ни открытия «на запись», ни записи
по смещению — поэтому потоковый диск объявлен read-only, и DOS получает отказ.

Вывод: **это не «в эталоне нет записи», а в нашем порте выброшен путь записи.**

## 4. Варианты решения

### A. Запись по смещению (правильный путь)
1. В `fat.c` добавить открытие файла на запись с состоянием: `fat_wstream_t`
   (первый кластер, текущий кластер, смещение внутри кластера, размер).
2. `fat_wstream_write(s, offset, buf, len)` — пройти цепочку кластеров до нужного
   смещения (как `fat_stream_read`), при необходимости дописать кластеры
   (продление цепочки) и обновить FAT.
3. `fat_wstream_flush/close` — сброс грязного сектора и обновление записи каталога
   (размер, время).
4. В `disks-h3.c.inl` добавить `write_cb` в `struct_drive`, снять `readonly`
   для образов, открытых на запись; в `bios_write` писать через него.
5. Кэш секторов (например, 32–64 сектора, write-back с flush по таймеру/выходу) —
   иначе каждая запись DOS = отдельный проход по FAT (и это же ускорит чтение,
   см. §5).

Риски: порча FAT при обрыве питания между обновлением данных и каталога;
частичная запись кластера. Нужен аккуратный порядок «данные → FAT → каталог»
и запрет записи при `readonly`-образе.

### B. Оставить read-only (быстрый путь)
- Явно монтировать C:/D: как read-only **на уровне BIOS** (не давать DOS
  пытаться писать) — тогда вместо «запись невозможна» будет корректный отказ
  или файл откроется только на чтение, если DOS это позволяет.
- Починить видимость B:/D:: число дисков в оборудовании BIOS и вызовы
  `pxt_disk_set` для drive 1 и 3 из `emu_run_pxt` (или из `pxt_dialog`).
- Не требует правок `fat.c`, но запись файлов остаётся невозможной.

### C. Оконные образы в RAM
Открывать HDD не целиком, а окнами (например, 4 МБ) с подкачкой при выходе за
границу окна. Запись идёт в RAM-окно, при вытеснении — на SD через `fat_write_*`.
Компромисс между A и B: сложнее A по логике, но не требует полноценного
write-at-offset (перезапись окна целиком последовательной записью).

## 5. Медленное чтение (отдельный дефект)

`slow ... us=247890` — это не «медленная SD», а по-секторный поиск: каждый
`fat_stream_read` заново проходит цепочку кластеров от начала файла. Для образа
256 МБ и 527 МБ это неприемлемо.

Лечится тем же кэшем секторов (п. A.5) плюс кэш позиции в цепочке кластеров
(запоминать последний кластер и его номер — DOS читает последовательно).

## 6. План проверки на стенде

1. `dir C:` и открытие файла — не должно быть «запись невозможна» (для A).
2. `copy` файла на C: и обратно, `chkdsk C:`, перезагрузка — файл на месте,
   FAT не разрушен.
3. `D:` (второй HDD) и `B:` (fdd1) — видны и открываются.
4. Замер: чтение 1 МБ подряд — среднее время на сектор должно упасть
   с ~7 мс (в кэше) и не иметь выбросов 250–460 мс.
5. Обрыв питания во время записи — образ открывается, `chkdsk` не находит
   потерянных цепочек (допустимо потерять последнюю запись).

## 7. Открытые вопросы

- Кто и когда открывает `hdd.img`/`hdd2.img` — `pxt_mount_hdd()` из
  `pxt_host.c:69-78` (stream) или `pxt_dialog`; от этого зависит, где брать
  write-колбэк.
- Нужна ли запись в принципе (если игры только читают) — тогда вариант B
  дешевле и безопаснее.
- Формат кэша и его объём: RAM есть (`.noinit_fbn` ≈105 МБ), но владелец один —
  кэш должен жить в пуле и освобождаться при выходе.
