## 1. Критические находки (требуют решения владельца)

### О-1. `gba_run_frame()`: звук читается ДО `execute_arm()` — «пачка» сэмплов
Файл: `h3_bare/cores/gba_host.c:185` (и `gba_host.c:191-194`)

Порядок в кадре:
1. `write_ioreg(REG_P1, …)` — ввод
2. `clear_gamepak_stickybits()` + `execute_arm(execute_cycles)` — **исполнение кадра**,
   внутри `update_gba()` в конце VBlank вызывает `render_gbc_sound()`
   (main.c:241), который нарабатывает НОВЫЕ сэмплы в `sound_buffer[]`.
3. `sound_read_samples(sndbuf, 549)` — читаем из `sound_buffer` **после** кадра.
   Это правильно.

**Проверено:** `update_gba` зовётся из `execute_arm` (cpu.cc:1536/3110/3593),
`render_gbc_sound()` вызывается при `vcount==228` (глав. main.c:241).
=> Звук читается ПОСЛЕ генерации. Ошибки НЕТ. (r571-лог «np≈0» — отдельный вопрос,
см. О-2).

### О-2. r571: временный printf в горячем цикле — тормоз и шум UART
Файл: `h3_bare/cores/gba_host.c:196-203`

```c
static u32 dbg = 0;
if ((dbg++ % 60) == 0)
    printf("gba snd: np=%u ring=%d\n", (unsigned)np, i2s_ring_level());
```

- `printf` в bare-metal идёт в UART **polling** (ждёт TX FIFO) — на 60 Гц это
  ~1 строка/с, но UART на 115200 бод проводит её ~0.6 мс — на каждый 60-й кадр
  добавляется заметная пауза (джиттер звука, микро-фризы).
- По правилам владельца «GitHub — не помойка» и «никаких временных трейсов
  в закоммиченном коде» — **удалить перед коммитом** (как делали для Lynx r561).

*Предложение:* убрать блок r571 целиком (или оставить под `#ifdef GBA_SND_DBG`).

### О-3. Слежение периода GBA (r562) — магические константы и «мёртвая» ветка
Файл: `h3_bare/cores/emu.c:487-506`

```c
uint32_t pairs_frame = 800;          // «60 Гц претплав»?? 800 пар == 16.7 мс
...
uint32_t peri = (uint32_t)(((uint64_t)dtime * pairs_frame) / dp);
if (peri >= 12000 && peri <= 24000)
    emu_period_us = (uint16_t)(((uint32_t)emu_period_us * 7 + peri) / 8);
```

Проблемы:
1. `pairs_frame=800` при GBA-звуке — на самом деле за кадр пушится ~804 пары
   (32768→48000). Число «800» совпадает со 804 с погрешностью, но:
   - dp — это **реальное** число пар, выведенное железом за кадр (из TX Sample
     Counter). Если кольцо пустое — железо выводит ТИШИНУ (0), dp всё равно растёт.
   - peri = dtime * 800 / dp — «сколько мкс железу нужно на 800 пар» — оценивает
     период, когда dp ≈ 800. Когда dp больше/меньше (а при 60 Гц и железе 48 кГц
     dp ≈ 800 — так и есть), формула даёт период ~16667. ОК по замыслу, но:
2. **«Мёртвая» ветка `if (dp)`** — dp всегда > 0 при `prev_txc && txc > prev_txc`,
   т.е. `if (dp)` лишний (компилятор, возможно, выкинет).
3. **Приваt-статика `prev_txc/prev_t` внутри блока** — при выходе в меню и
   повторном входе сохраняется предыдущее значение, но сброс периода на выходе
   (r562: `exit: emu_period_us = 16667`) — а статики НЕ сбрасываются, ок, но
   первый кадр после входа имеет `prev_txc=0` => скачок. Не критично.

*Предложение:* переписать по образцу Lynx (r559/r560): `peri = dtime*800/dp`,
убрать `pairs_frame` и лишний `if(dp)`. И главное — НЕ смешивать «слежение
периода» с «обрезкой кольца»: обе логики в одном кадре — хрупко.

### О-5. r563: open-bus NOP — `ws_cyc_seq[(PC>>24)&0xF][1]` для PC≥0x10000000
Файл: `h3_bare/cores/gba_sp/cpu.cc:3100` (ARM) и `3583` (Thumb)

При `pc_address_block == NULL` (PC ≥ 0x10000000) выполняется NOP, но в конце
итерации:
```c
cycles_remaining -= ws_cyc_seq[(reg[REG_PC] >> 24) & 0xF][1];
```
`(reg[REG_PC] >> 24) & 0xF` для PC ≥ 0x10000000 (т.е. биты 28-31):
- 0x10000000..0x1FFFFFFF → region 0x1
- 0x20000000..0x2FFFFFFF → region 0x2 (EWRAM!)
- 0x30000000..0x3FFFFFFF → 0x3 (IWRAM)
- 0x40000000..0x4FFFFFFF → 0x4 (IO)
- 0xF0000000..0xFFFFFFFF → 0xF
Все эти ячейки `ws_cyc_seq[*][1]` ≥ 1 (кроме region 0x0, 0x1, 0x8-0xD = 0!).

**Риск:** для PC в диапазоне 0x08000000..0x0FFFFFFF (регион 0x8-0xD, ws=0!)
`cycles_remaining -= 0` → **бесконечный цикл NOP** без продвижения времени —
игра «висит» (не выходит по ESC, т.к. эмуляция не возвращается).

Но это возможно ТОЛЬКО если PC попал в 0x08000000..0x0FFFFFFF, а страница не
замаплена, т.е. `pc_address_block == NULL` при pc_region<8192 — а там r563
ставит `pc_address_block = load_gamepak_page(...)` (не NULL). ОК — для легальных
регионов NULL не возникнет. Для ≥0x10000000 cost ≥1 всегда => цикл конечен.

**ВЫВОД:** бесконечного цикла нет, но есть **неточность**: open-bus NOP имеет
реальную стоимость 1 cycle, а мы списываем ws_cyc_seq[region][1] (для 0x4 = 1,
для 0xE/0xF = 1). Нормально. НО: `check_pc_region()` при переходе в ≥0x10000000
выставляет `pc_address_block=NULL`, а в `arm_loop` после NOP снова
`check_pc_region()`. Если PC _не меняется_ (NOP не двигает PC вверх адреса?..)
— смотрим: NOP = `MOV r0,r0` — PC увеличивается на 4 (arm_next через
`reg[REG_PC] += 4`), так что PC растёт, цикл конечен. **ОК, ошибок нет.**

*Однако*: в `arm_loop` при `pc_address_block==NULL` opcode=0xE1A00000 (MOV r0,r0)
**выполняется** (декодируется и исполняется), но:
- это НЕ настоящий open-bus (там был бы BUS_VALUE, а не NOP).
- Побочный эффект: `using_instruction(arm)` увеличивает `instruction_count` и
  может дёрнуть `process_cheats` — не критично.

*Замечание:* поведение корректно и не виснет. При желании можно списывать
фиксированную 1 такт вместо ws_cyc_seq — для чистоты.

### ~~О-6. OOB memory_map_read~~ — СНЯТО (ложная тревога)
Первоначально показалось, что `map_rom_entry` пишет в `memory_map_read[16384+]`
за пределы `[8192]`. Перепроверка:
`0x8000000 >> 15 = 4096` (НЕ 16384!), `0xA000000 >> 15 = 5120`,
`0xC000000 >> 15 = 6144`. Массив `[8192]` покрывает индексы 0..8191
(адреса 0x0..0x10000000). Максимальный индекс записи для 4МБ ROM = 6655
(< 8192). **OOB нет — замечание снято.**

### О-7. `read_open*` при PC с open-bus и `fetch_is_open_bus` — корректно, но…
Файл: `gba_memory.c:642-690`

`fetch_is_open_bus(a)` возвращает true для `(a>>24) > 0x0F` (≥0x10000000) и для
`(a>>24)==0x01` (0x01000000..0x01FFFFFF) и `(a>>24)==0x00 && a>=0x4000`.

Но data-обращения к диапазону 0x0E000000..0x0FFFFFFF (регионы 0x0E/0x0F) идут
в `read_backup()` (сейвы SRAM/EEPROM), а НЕ в open-bus. Т.е. определённые
Android-игры, читающие 0x0E/0x0F как «backup», получают сейв-область, а на
железе это open-bus. Не критично для наших ROM.

## 2. Средние/логические замечания

### С-1. `emu_throttle()`: период меньше реального времени кадра — дрейф
Файл: `h3_bare/cores/emu.c:186-217`

Если эмуляция кадра занимает больше `emu_period_us` (тяжёлая сцена), то
`left = emu_period_us - elapsed` отрицателен → `while(left>0)` не выполняется,
звук не доливается вообще, и `emu_ts0` ставится в now — следующий кадр без
компенсации. При стабильно тяжёлом кадре звук «молчит» (кольцо пустеет → I2S
пишет тишину). Рекомендация: при `elapsed >= emu_period_us` всё равно делать
один `i2s_flush_max(24)` для подкачки звука (не дожидаясь следующего кадра).

### С-2. `i2s_push_sample` drop-on-full — потеря при пиковых пачках
Файл: `h3_bare/cores/i2s.c:184`

```c
if (ring_count() >= AUDIO_RING_SIZE) return;   // drop-on-full
```
Кольцо 8192 пар = ~170 мс. При GBA-пачке ~804 пары/кадр и периоде 16667 —
не переполняется. Но при сбое темпа (r562 слежение) может. Приемлемо, но
лучше бы зажать: если полное — сдвинуть rd (drop старых), как в i2s_ring_trim.
Опционально.

### С-3. DC-блокер: `dc_l` затирается только `i2s_ring_reset()`
Файл: `i2s.c:106`

`i2s_ring_reset()` обнуляет dc_l/dc_r — вызывается в `emu_prepare()` (emu.c:169).
При смене системы — ок. Но при `i2s_ring_trim()` (в GBA/Lynx) dc не трогается —
небольшой щелчок в момент trim. Можно сбросить dc при trim тоже. (мелочь)

### С-4. «r571-лог» и «r572-порог» — параметры тюнинга, не код
Порог среза `7800` (emu.c:511) и `4000` (emu.c:570) — «магические», пометить
#define с комментарием «подобрано на стенде, менять осознанно».

### С-5. `emu_esc_hold()`: `usb_kbd_get_last` после `usb_kbd_get_raw` в ядре
Порядок в кадре GBA: `gba_run_frame()` → `gba_buttons()` (вызывает
`usb_kbd_get_raw`) → `emu_esc_hold()` (вызывает `usb_kbd_get_last`).
- `get_raw` делает `kbd_scan()` (аппаратный полл, обновляет g_held).
- `get_last` НЕ делает полла, читает тот же g_held.
=> консистентно, повторного полла нет. **ОК** (комментарий r0.221 соблюдён —
два `get_raw` за кадр не происходит).
