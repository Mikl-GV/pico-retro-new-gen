## КРИТИЧЕСКИЕ КРОСС-ФАЙЛОВЫЕ ОШИБКИ (подробно)

### К1. «Орфанная» BSS-зона libstdc++/newlib НЕ ОБНУЛЯЕТСЯ — адрес краша Coleco

**Физика:** `platform/linker.ld` собирает `.bss : { *(.bss); *(COMMON) }`.
Всё, что компилятор положил в `.bss.*` (libstdc++ local-statics локали/iostream,
newlib `__sf`, `errno`, tz/malloc locks; объекты собираются с `-fdata-sections`),
линкер НЕ кладёт в выходную секцию `.bss`, а размещает «orphan»-ом сразу за ней,
на голой location-counter арифметике. `startup.S:225-231` обнуляет только
`_bstart1.._bend1`, поэтому зона `_bend1.._gb_heap_start` содержит мусор DRAM:

```
_bend1                    = 0x41FEB87C   (конец .bss, обнуляется)
_ZN12_GLOBAL__N_1L…locale  = 0x41FEB884 .. 0x41FEC400   ← НЕ обнулён
_ZGVZ…get_locale_mutex    = 0x41FEC7DC   ← guard-переменная, мусор
__sf (stdio FILE x3)      = 0x41FEC970   ← мусор
errno / __lock_*          = 0x41FECC90 .. 0x41FECCD0
_gb_heap_start            = 0x41FECCE0   (куча 24 МБ)
```

**`D:41FEC35C` находится ровно в этой зоне** (0x3880 байт ДО начала кучи,
между фасетами `ctype_wE`=0x41FEBE90 и `messages_cE`=0x41FEC370).
Гипотеза «падение внутри gb-heap после new GearcolecoCore()» из исходного
задания НЕ подтвердилась — куча начинается с 0x41FECCE0.

Триггер: `coleco_host.cpp:78` → `GearcolecoCore::Init` (`GearcolecoCore.cpp:90`)
→ `Log(...)` → `Log_func` (0x403043E8) → **newlib `puts`** → newlib stdio/locale
использует необнулённые `__sf`, guard-переменные, locks. Мусорный guard → фасет
не инициализируется → дикие указатели; мусорный `_bf._base` → запись по
произвольному адресу (попала в 0x41FEC35C). «Поток нулей» после краша —
симптом того же: инициализация фасетов молча скипается.

### К2. `gb_alloc` выравнивает только до 4 байт, код делает 8-байтовые доступы

`gameboy_stubs.c` — bump-аллокатор с `sz = (sz + 3) & ~3`. База кучи 32-кратна,
НО каждая последующая аллокация даёт объекты по 4-mod-8:

```
GearcolecoCore  0x41FECCE0
Cartridge       0x41FECD40
Random          0x41FEE568
Memory          0x41FEE56C
Processor       0x41FEE5EC
Audio obj       0x41FEF04C  ← &7 == 4
F18A  obj       0x41FEF238  ← &7 == 4
```

В Gearcoleco:
- `Audio::Init` (0x400D5CB8): `ldrd r0, [r4]` — 64-битное чтение по 4MOD8.
- F18A-конструктор (0x400FFEF8): `vstr d18, [r4, #112]` — 64-битная запись по 4MOD8.

Если SCTLR.A=1 — Data Abort с DFSR=alignment на первом же доступе.
Даже при A=0 это UNPREDICTABLE. Затрагивает все C++-ядра (Lynx/Handy, A7800).

### К3. `--allow-multiple-definition` + newlib libc

`Makefile` линкует `-nostdlib … -lstdc++ -lgcc -lc -lm -lgcc
--allow-multiple-definition`. Подтверждено nm r179:
- `malloc` = 0x4001168C (gameboy_stubs) — первые определения побеждают;
- при этом в ELF есть вся машинерия newlib malloc (`__malloc_av_` = 0x405026A0,
  `__malloc_current_mallinfo` = 0x41FECCA4 — см. К1, не обнулена!);
- newlib stdio (`puts/fflush/fputs` слинкованы реально) вызывает `malloc` →
  bump-пул эмуляторов.

Следствие-бомба: `coleco_host.cpp:75` `gb_heap_reset()` отматывает пул на 0
при каждом запуске; newlib держит указатель stdio-буфера stdout в старом
участке пула → **второй запуск системы с newlib-puts затирает живой
stdio-буфер данными нового эмулятора** → corruption.

### К4. Флаг «игра активна» (0x74) не выставляется в обычном пути Enter

`rom_browser.c:575-577` — обычный Enter: `load_rom(...) → emu_clear_fb() →
run_emulator(...)` БЕЗ `*(volatile uint32_t*)0x74u = 1;`. Флаг ставится только
в чит-меню пути (`rom_browser.c:540`). В `run_emulator` (50-113) установки нет.

Следствие: во время игр, запущенных обычным Enter, CPU1 не заморожен
(`tft_drv.c:1156` не срабатывает) → тач-скан/рендер дёргают `PA_DAT` (PA21/PA2),
а Sega-пад (PA11/PA12) в это время сканируется в каждом кадре → RMW-гонка,
которую r162 должна была убрать, осталась в главном пути запуска.

## СКРЫТЫЕ И НЕЯВНЫЕ ПРОБЛЕМЫ

1. **`_gettimeofday`** (`libc_min.c:190`) не пишет `tv` — newlib `time()` при
   «успехе» читает неинициализированный стек → `Seed((u32)time(NULL))`
   (`GearcolecoCore.cpp:96`) получает мусор. Стаб должен хотя бы обнулять tv.
2. **`tft_touch_scan`** (`tft_drv.c:835-836`) — деление на `(xmax-xmin)` /
   `(ymax-ymin)` без guard; при испорченной калибровке — деление на 0 → UNDEF.
3. **`mmc_wait_rint`** (`sd.c:71-78`) при таймауте не чистит RINT; `read_chain`
   (`fat.c:68-98`) возвращает «сколько прочитали» без признака обрыва —
   `load_rom` может запустить обрезанный ROM.
4. **`__sync_val_compare_and_swap_4`** (`libc_min.c:98`) — не атомарная
   заглушка; guards libstdc++ (`__cxa_guard_acquire`) на неё опираются.
5. **`delay_ms`** (`tft_drv.c:371`) — `(int32_t)`-сравнение: корректно до
   wrap'а 32-битного мкс-счётчика (~44 000 с) — не критично, отметить.
6. **RMW-гонка `PA_DAT`** между CPU0 (PA11/12, PA15) и CPU1 (PA21/PA2) —
   задокументирована в коде, смягчена кэшами и заморозкой, но НЕ устранена
   (усугубляется К4).

## ВАРИАНТЫ ИСПРАВЛЕНИЙ (НЕ ПРИМЕНЕНЫ — ждём «да»)

### F1. Закрыть дыру обнуления BSS (К1) — root-fix
`h3_bare/platform/linker.ld:45-50`:
```ld
  .bss :  {
    _bstart1 = . ;
    *(.bss); *(.bss.*); *(COMMON);   /* добавить .bss.* — иначе orphan-зона не zero */
    . = ALIGN(4);
    _bend1 = . ;
  }
```
После этого `_bend1` ≥ 0x41FECCD8, `startup.S:225-231` обнулит и локали,
и `__sf`, и locks; `_gb_heap_start` линкер пересчитает автоматически.
Адреса в `docs/ARCHITECTURE.md` поправить после сборки по `nm`.

## И. Стендовая сессия BK-0010/0011М — r0.243…r0.253 (2026-09-28)

Режим: итеративная отладка по стенду (UART), нативные прогоны ядра (x86) на тех же
комплектах (gc-sections, bump-аллокатор, наша libc_min) — краха на нативно НЕТ, т.е.
проблема была в окружении H3 (линковка всех ядер вместе), а не в ядре/ROM.

### И.1. Симптом «BK: … P:»+мегабайты «нулей» — ДВА разных бага

1. **Бесконечный вывод '0' (флуд)** — `hex32_uart` (startup.S) держал счётчик цикла в `r1`,
   а `uart_dbg` его затирает (`ldr r1,=UART_USR/THR`) → цикл не заканчивался и после 8
   цифр лил '0' вечно. Именно поэтому «нули», и именно поэтому F1..F6 (r0.185, «поток нулей»)
   и P:-строки тонули. Исправлено r0.249: счётчик на стеке; `hex8_uart` тоже чинился
   (младшая цифра IFSR/DFSR всегда была '0').

2. **Реальный prefetch abort («P:00000000:0E»)** — хостовый PC уходил в 0. Ключ дала
   диагностика r0.250: метки стадий («run loop enter» / «input_poll» / «in_done» /
   «in_state» / «video_refresh») показали, что падение между `input_poll_cb()` и `video_cb()`;
   r0.251 добавил в `_prefetch` чтение **banked LR SVC** («BL xxxxxxxx») → `BL 401799DC`
   — адрес внутри **`tty_poll`**: там `ldr r4,[#0x41583AFC]; blx r4`, а `input_state_cb`
   == **NULL**.

   Причина: у ядра BK глобальные имена ЛИБРЕТРО-колбэков (`input_state_cb`, `environ_cb`,
   `video_cb`, `audio_cb`, `input_poll_cb`) и I/O-функций (`io_init`, `sound_init`,
   `tape_write`, `joystick_init`, `mouse_read/write`, `disk_write`) коллизируют с такими же
   именами других ядер под `--allow-multiple-definition`. Линкер отдаёт имя первому,
   а ссылка из **другого объекта** (`tty-libretro.o` → extern) привязывается к ЧУЖОЙ ячейке,
   которую наш сеттер не заполняет → NULL → `blx 0`. Нативно (одно ядро) коллизий нет —
   потому и не воспроизводилось.

   **Исправление (r0.252):** `bk_rename.sh` дополнен — все коллизирующие имена
   переименовываются в `bk_*`. Проверка после линковки:
   `undefined-символы bk-объектов ∩ определения не-bk объектов = 0` (r0.252, потом r0.253 — 0).
   Проверено дизасмом: сеттер и `tty_poll` теперь ходят в одну ячейку `bk_input_state_cb`.

- Запуск и кадры: **ДА** — ядро исполняет FOCAL, BKTRAP (EMT/TRAP/illegal — штатные вызовы

### И.4. Выводы для будущих ядер

- При интеграции libretro-ядра ОБЯЗАТЕЛЬНО проверять кросс-линковку:
  `undefined-символы ядра ∩ определения других ядер = ∅` — иначе `--allow-multiple-definition`
  тихо привязывает extern к чужой ячейке (симптомы: NULL-call → prefetch abort, «залипания»,

- `uart_dbg` в startup.S затирает r1/r2/r3 — вспомогательные функции, зовущие его,
  обязаны держать счётчики/значения в r4/стеке (или перезагружать из памяти).

## Л. r0.392 (2026-09-30) — ZX Spectrum и MSX: диагностика загрузки, кириллица

Разбор трёх жалоб пользователя: (1) ZX «не могу грузить ром»; (2) MSX «должны работать большие ROM, точно ли MSX2?»; (3) MSX «не ввожу все символы как на Ямахе; в русских играх мусор вместо надписей (Лабиринт)».

### Л.1. ZX Spectrum: почему «не грузится» и что сделано

**Корень:** `fuse/src/libretro.c:retro_load_game()` вызывал `utils_open_file()` и **игнорировал возврат**. Если файл не опознан ядром (не .z80/.sna/.tap/.tzx/.dsk/.scl/.trd/.dck/.ipf/.zip/.m3u; или битый «AB»-заголовок) — Fuse «успешно» стартовал в пустой BASIC, без единого сообщения (host_log был заглушен). Пользователь видел «запустилось, но не грузится».

**Применено:**
| # | Файл | Правка |
|---|------|--------|
| L1 | `fuse/src/libretro.c` | Новый глобал `int fuse_content_load_ok`; в `retro_load_game()` (основной и M3U-путь) — `fuse_content_load_ok = (utils_open_file(...) == 0)` |
| L2 | `fuse_host.c` | Pre-check расширения ДО загрузки: неизвестный формат → красно-жёлтое сообщение на экране «FUSE: не распознан формат» + список поддерживаемых + возврат в меню (не вход в эмулятор) |
| L3 | `fuse_host.c` | Предупреждение «файл больше памяти модели» для сырых образов (не снапшот/лента/диск) на 16K/48K-моделях: `fuse_model_ram()` (16K→16384, 48K→49152); подсказка «выбери 128K-модель» |
| L4 | `fuse_host.c` | После `fuse_retro_load_game()`: если `fuse_content_load_ok==0` — видимое сообщение «FUSE: файл не загрузился» + пауза → возврат в меню |

**Что это даёт:** любой файл, который ядро не может загрузить, теперь ПОКАЗЫВАЕТ причину на экране и в UART, вместо «молчаливого BASIC».

### Л.2. MSX: машина и большие ROM

**Ответ на «точно ли MSX2?» — ДА.** `msx_host.c` стартует `StartMSX(MSX_MSX2|MSX_PAL|MSX_MSXDOS2|MSX_GUESSA|MSX_GUESSB, RAMpg=4, VRAMpg=4)` — V9938 (MSX2), 128 КБ RAM + 128 КБ VRAM, PAL 50 Гц, BIOS MSX2.ROM+MSX2EXT.ROM вшиты и грузятся (StartMSX:712-732 не откатывается). Появилась читаемая строка в логе: `MSX: machine=MSX2 (V9938) PAL 50Hz RAM=128KB VRAM=128KB`.

**Большие ROM (мэпперы >128K):** сам fMSX их умеет (LoadCart: 8KB-страницы → ROMMask → GuessROM по характерным адресам 0x5000/0x9000/0xB000 (Konami5), 0x4000/0x8000/0xA000 (Konami4), 0x6000/0x6800/0x7000/0x7800/0x77FF (ASCII8/16)). Реальные причины «не грузится» у пользователя — не размер, а:
- **файл в ZIP** (начинается с 'PK') — LoadCart грузит только сырой .rom;
- **нет «AB»-заголовка** (0/0x4000/последняя-1 8KB-страница) — LoadCart принципиально отказывает (MSX.c:2999).

**Применено (msx_host.c):** перед `LoadCart` проверки `PK`/`AB` с явными WARN в UART; после `LoadCart` — лог `mapper=N` (ROMType[0]) и при `lr<=0` — красное сообщение на экране «MSX: картридж не загружен + причина»; имя файла выводится (g_cart_name).

### Л.3. MSX: кириллица — ввод и «мусор» (Лабиринт)

**Найдено по коду:**
- Текстовые режимы V99x8 рендерятся из VRAM-паттернов (Common.h RefreshLine0:519 `ChrGen`; RefreshLineTx80:940) каждый кадр — **игровые русские шрифты, загруженные в паттерны, эмулятор отображать умеет** (FontBuf/CYRILLIC.FNT не используется, MSX_FIXEDFONT не включён). То есть «мусор» — не тупой кэш шрифта; вероятные причины — режим/палитра конкретной игры либо битый дамп. Нужен стенд (захват кадра), статически не воспроизводится.
- **Ввод:** физически на YIS-503II русские буквы стоят на тех же клавишах, что латиница, и русские игры читают МАТРИЦУ (не CHGET) — сканкоды уже совпадают с железом. Ограничение: программы, берущие символ через CHGET/BIOS, получат ЛАТИНИЦУ (западный MSX2.ROM), полноценная кириллица через CHGET требует советской BIOS-прошивки (отдельная задача).

**Применено (msx_host.c):** переключатель **F9** «RU/LAT» — печатает фонетическую раскладку YIS-503II в UART и рисует OSD-подсказку на кадре 2.5 с:
```

    A=А S=С D=Д F=Ф G=Г H=Х J=Й K=К L=Л
    Z=З X=Ь C=Ц V=В B=Б N=Н M=М
```

## У. r0.401 (2026-09-30) — МС1504: краш DFAR=0x15 (коллизия `timing`)

Со стенда: МС1504 грузит BIOS PK300, BIOS шлёт OUT на COM/LPT (03F8/03FB),
затем Data Abort `F1=00000015 F2=21 … F5=40178870`. F5(F6—LR) 0x40178870 —
внутри функции `timing` по адресу 0x40178868, которая ЧИТАЕТ [r0,#18] при r0≈3
→ DFAR=0x15.

**Корень:** символьная коллизия под `--allow-multiple-definition`: `timing`
определён и в fake86-сеть (наш `ms1504_shim.c` — пустая заглушка), и в ядре
**BK** (`bk/timing.c`, функция с указателем на структуру ТВ/тайминга).
Линкер берёт ПЕРВОЕ определение — чужая функция с аргументом, а fake86 звал
`timing()` без аргументов → мусор в r0 → чтение по r0+18 ≈ 0x15 → Data Abort.

**Решение (штатный механизм коллизий проекта, как cps1/fuse/bk):**
- `ms1504_rename.sh` (новый, батч): по всем объектам набора собирает список
  сильных глобалов и переименовывает их в `m15_` — согласованно определения
  и ссылки во ВСЕХ объектах; KEEP: `emu_run_ms1504`, вшитые дампы.
- Makefile: четыре правила собирают `.o` без переименования; отдельный stamp
  `ms1504_renamed.stamp` (зависимость ELF) после сборки всех объектов запускает
  батч.
- Первая попытка (переименование в каждом объекте по отдельности) дала
  undefined refs: ссылки на `vidmode` и др. остаются, т.к. rename не видел
  чужих определений — батч по набору решает.

**Проверка ELF r0.401:** `m15_timing/m15_exec86/m15_RAM/m15_cpu/m15_vidmode/
m15_readVGA/m15_writeVGA` на месте; `timing` (BK) остался; `emu_run_ms1504`

## Ф. r0.403 (2026-09-30) — МС1504: HLT-зависание BIOS (нет IRQ0)

Со стенда: после инициализации COM/LPT BIOS PK300 уходит в HLT —
`BIOS: critical warning, HLT outside of trap area?!` + бесконечное
`CPU: HALTED!!!!!`. Это НЕ крыша ядра: внешний BIOS честно выполняет HLT
(ожидание прерывания), а fake86 снимает HLT только по IRQ при
`cpu.ifl && (i8259.irr & ~i8259.imr)`. Наш шим `timing()` был пустым —
PIT IRQ0 НЕ генерировался → HLT зависал навсегда. (Родной timing.c тянет
SDL и аудио.)

**Применено:**
- `ms1504_shim.c`: реальный `timing()` на HSTMR:
  - IRQ0 (`doirq(0)`) при `i8253.active[0]` раз в 54925 мкс (~18.2 Гц, как
    PIT 1.19318 МГц/65536) — HLT просыпается, BIOS-таймеры идут;
  - порт 3DA (CGA-статус): бит3/бит0, переключение ~120 Гц — видео-циклы,
    ждущие ретрейс, не вешаются.
- `ms1504_rename.sh` сделан **идемпотентным** для инкрементальной сборки:
  канон имён строится по ВСЕМ объектам со снятием префикса m15_ (m15_RAM →
  RAM), в объекте переименовываются только голые вхождения; смешанные
  состояния (часть объектов уже с m15_, часть свежая) больше не ломают
  линковку (до этого: свежий shim.o с «голыми» doirq/port3da не находил
  переименованные m15_doirq/m15_port3da → undefined refs).

**Проверка ELF r0.403:** `m15_doirq`, `m15_port3da`, `m15_timing` на месте;
`timing` (BK) не тронут. Сборка 0 ошибок, `h3_bare.bin` 13 518 452 Б.

## Х. r0.404 (2026-09-30) — МС1504: HLT не просыпался (гейт timing по totalexec)

r0.403 (IRQ0 от HSTMR) не помог: `CPU: HALTED!` без конца. Диагноз по коду
`exec86()` (cpu.c): чтобы HLT проснулся, нужен IRQ, а IRQ генерирует
`timing()`, который вызывался `if ((totalexec & TIMING_INTERVAL)==0)`.
**`totalexec` при HLT НЕ растёт** (инкремент только в путях исполнения
опкодов) → если в момент HLT totalexec&15≠0, timing() больше не вызывается
→ IRQ0 не приходит → вечный HLT.

**Применено (вендорная правка `cpu.c`, стоковый код тоже был завязан на это):**
- гейт `timing()` переведён на `loopcount` (счётчик внешнего for — растёт
  всегда, в т.ч. в HLT) → PIT IRQ0 (наш шим, 18.2 Гц) доходит до CPU в HLT;
- флуд `CPU: HALTED!!!!!` заглушен (печать раз в 1024 итераций).

Wake-условие (стр. 1460) не менялось: `cpu.ifl && (i8259.irr & ~i8259.imr)`
— проснётся, когда BIOS разрешит прерывания и размаскирует IRQ0.

**Сборка r0.404:** 0 ошибок; `h3_bare.bin` 13 518 484 Б. Символы те же
(m15_* схема не менялась). На стенде: «MS 1504» → «Встроенное ПО» — BIOS

### Б2. MS1504 — HLT с запрещёнными прерываниями (ifl=0)

**Симптом (r0.404+ плнд):** BIOS PK300 (вшит) проходит COM/LPT-инициализацию и
выполняет `HLT`; `CPU: HALTED! ifl=0 imr=00 irr=02 pit=0`:
- **ifl=0** — IF сброшен (CLI) → штатный wake по IRQ НЕ работает (exec86
  будит только `cpu.ifl && irr&~imr`);
- **imr=00** — PIC все IRQ размаскированы;
- **irr=02** — IRQ1 (клавиатура) уже на шине;
- **pit=0** — PIT канал 0 не запрограммирован (наш IRQ0-генератор
  завязан на i8253.active[0] → молчит).
Реальный 8086 с IF=0 так же спит до NMI/reset — т.е. BIOS ждёт, вероятно,
NMI (или ответа контроллера клавиатуры через IRQ1 при IF, который BIOS
считает включённым, но не включил).

**Как вернуться:** варианты: (а) генератор NMI в шиме (nmi-эмуляция), (б)
принудительно `cpu.ifl=1` перед HLT (грубо, но POST сдвинется), (в) разобрать,
чего ждёт BIOS PK300 на этом шаге (IRQ1-ACK клавиатуры — подать скан/ответ).
Текущее состояние: r0.408 собран; диагностика `HALTED ifl/imr/irr/pit` уже
печатается.

### Я.1. Термоконтроль и вентилятор (новый модуль `cores/ths_fan.c/.h`)

**Датчик THS H3** (по драйверу linux `sun8i_thermal.c`, H3-профиль):
- база `0x01C25000`: `THS_CTRL0`=0x00, `CTRL2`=0x40, `IC`=0x44, `MFC`=0x70,
  `TEMP_DATA`=0x80;
- такты (ccu-sun8i-h3): bus gate `0x068` bit8, reset `0x2D0` bit8, mod clk
  `0x074` (gate bit31, div=1 → osc24M);
- инициализация как `sun8i_h3_thermal_init`: MFC=0x5 (фильтр 4 сэмпла),
  IC=(365<<12)|0x100 (период ~0.25 с), CTRL0=479 (T_acq 20 мкс), CTRL2=479<<16|1;
- формула: **t[м°C] = 217000 − (reg·1211)/10** (reg = 12 бит TEMP_DATA);
- калибровка: дефолт 0x800 (SID-калибровку не читаем — для порога ±~2°C не нужна).

**Вентилятор** (пины выбраны из свободных на OPI Lite):
- **PA6 = управление** (выход; HIGH вкл через транзистор/MOSFET);
- **PA7 = FG (тахо)** (вход, pull-up; open-drain датчик вентилятора);
- перепады FG считаются каждый кадр из `fb_flush()`, RPM раз в 1 с:
  `RPM = (перепадов/с)·60/4` (4 перепада FG = 1 оборот у 2-импульсного тахо);
- гистерезис: вентилятор вкл при ≥60°C, выкл при ≤50°C;
- оверлей: при ≥55°C в правом верхнем углу HDMI-FB поверх кадра
  (`54.3C F3120r`), жёлтый/оранжевый/красный (≥85°C);
  рисуется ДО clean D-cache в `fb_flush()`, поэтому попадает в текущий кадр.

Подключение вентилятора: 3-проводный (GND, +5V, FG→PA7) или 4-проводный
(+12/5V, GND, FG→PA7, PWM/CTL→PA6 через транзистор). Схема/пины пометить в
README (FAN: PA6=CTL, PA7=FG).

**Проверено на железе?** — НЕТ (стенд занят). Логика регистров сверена с
драйвером Linux; первое включение покажет `THS: init ok` и температуру на
экране при перегреве. Если температура «прыгает или не читается» — снимать
`raw` и сверить с формулой (в UART добавить raw по запросу).

### Я.2. Sega 16 «подтормаживает» — что найдено и сделано

Статический разбор `run_cps` показал, где проводился каждый кадр (без стенда
точные цифры не измерить — добавлена диагностика, см. ниже):
- **полный редрау 1024×600 каждый кадр**: `host_render_frame` заливал ВСЕ поля
  (верх/низ/лево/право) через `for` каждый кадр + пиксельный цикл с 3 сдвигами
  на пиксель (RGB565→XRGB8888);
- **fb_flush** чистит 2.4 МБ D-cache каждый кадр — неизбежно для целостности;
- **двойной скан геймпада** (host_update_input + emu_esc_hold раз в 50 мс) —
  задокументировано ранее, не трогали;
- throttle уже привязан к `nBurnFPS` (r0.391) — биения фаз 60 vs 59.6 Гц убраны.

**Применено (r0.411):**
| Правка | Файл | Что |
|---|---|---|
| P1 | `cps1_host.cpp` `host_render_frame` | **Кэш полей**: чёрные поля перезаливаются только при СМЕНЕ геометрии кадра (x0/vw/vh/y0) — внутри игры геометрия стабильна, экономия ~половины записей FB на кадр |
| P2 | `cps1_host.cpp` | **LUT RGB565→XRGB8888** (65536×4 Б): пиксельный цикл без сдвигов/масок на каждый пиксель |
| P3 | `cps1_host.cpp` main-loop | **Диагностика таймингов** (раз в 256 кадров `CPS: fr=… avg core/render/flush us`) — **снята r0.414** (роль выполнена, шумела в логе) |

**Замер со стенда (NeoGeo MVS, 304×224, r0.412):**
`avg core≈6700us render≈6800us flush≈1220us total≈17000us` (период 16897 мкс) —
кадр на пределе периода (~17 мс vs 16.9 мс). **Главный кандидат — render ≈ 6.8 мс**
(LUT/кэш полей уже применены; дальнейшее: частичный clean flush, либо буфер
800×600). Это общий профиль всех CPS-семейств, не только S16.**

### Я.5. r0.414 — отзыв диагностики таймингов, уборка мусора

По просьбе пользователя:
- **Снята печать `CPS: fr=… avg core/render/flush us`** (r0.411 P3) — шумела в
  логе каждые 256 кадров. Роль выполнена: замер со стенда показал
  render≈6.8 мс/кадр — главный кандидат дальнейшей оптимизации (см. Я.2).
- **Оверлей температуры** (r0.411): в правом верхнем углу HDMI, при T ≥ 55°C,
  цвет жёлтый → оранжевый (≥60°C) → красный (≥85°C), при работе вентилятора
  добавляется RPM (`54.3C F3120r`). Подробности в HARDWARE.md.
- **Бут-лог инициализации джоя/кнопок** возвращён (r0.412): `sega_pad: init OK`
  и `PAD: i2c scan: 0x20=… 0x27=…` — печатаются один раз при старте;
  шумные `PAD: buttons->…` и `PAD: pull-ups …` убраны (r0.413).
- **i2s.c приведён к схеме пользователя** (PA18/19/20 + PG7, НЕ PA10-12 как
  было в коде — те заняты Sega-падом!). Звук к хосту не подключён (r0.413,
  HARDWARE.md).
- **В /tmp/gigatool почищено** (после эксперимента с нативным MSX-харнессом):
  все артефакты и логи сборки удалены, мусора не осталось.

Правки r0.412-r0.414 не коммитились (по правилам проекта).
