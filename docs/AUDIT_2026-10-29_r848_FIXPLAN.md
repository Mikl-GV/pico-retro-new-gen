## 1. Правила выполнения дельт

1. Одна дельта = один пункт плана. Никаких попутных рефакторингов и переформатирования.
2. Перед дельтой: `git status` чистый; после — `make clean && make -j$(nproc)`.
   (`Makefile:10-12`: зависимостей от `.h` нет, поэтому `clean` обязателен.)
3. После сборки — проверка на стенде по разделу дельты (ниже). Без стенда дельта не считается принятой.
4. При регрессе — `git checkout -- <файлы>` и возврат к предыдущей ревизии; версия не повышается.
5. Каждая принятая дельта: инкремент `g_fw_version` (`main.c:336`) и строки `build:` (`main.c:344`), короткая запись в `docs/HANDOVER.md` (после D9 — в сокращённый HANDOVER).
6. Все правки комментариев — строго по коду; «хвосты» и предположения не оставлять (правило `AGENTS.md`).

Нумерация версий: D1 → r849, D2 → r850, D3 → r851, D4 → r852, D5 → r853, D6 → r854, D7 → r855, D8 (если меняется код) → r856, D9 → r857.

## 3. Дельты: суть, патчи, проверки

### D1. FTP: переполнение `LIST` и песочница `/roms`

**Проблема 1 (Critical).** `net_ftp.c:296` `char body[4096]`; циклы останавливаются на `bl == 4095`, затем `:323`:
```c
body[bl++]='\r'; body[bl++]='\n';
```
второй `body[4096]` — запись за массив на стеке. Достаточно ~36–40 записей с именами по 80 символов (`:321`).

**Патч 1** (`net_ftp.c:303-324`):
```c
for (int i = 0; i < n && bl + 2 <= sizeof(body); i++) {
    ...
    if (bl + 2 > sizeof(body)) break;
    body[bl++] = '\r';
    body[bl++] = '\n';
}
```
(остальные внутренние проверки `bl < sizeof(body)-1` оставить).

**Проблема 2 (Critical).** `make_path()` (`:70-113`) пускает абсолютный путь как есть, а `CWD/STOR/RETR/DELE` (`:231-385`) не проверяют, что путь внутри `/roms`. Комментарий `:69` («не даём уйти за /roms») коду не соответствует.

**Патч 2.** Ввести хелпер и применять его в `make_path` после нормализации:
```c
static int path_in_root(const char* p) {
    return (strcmp(p, "/roms") == 0) || (strncmp(p, "/roms/", 6) == 0);
}
...
/* конец make_path: */
if (!path_in_root(out)) {
    char t[FAT_NAME_LEN];
    const char* tail = (out[0] == '/') ? out : "/";
    snprintf(t, sizeof(t), "/roms%s", tail);
    strncpy(out, t, (size_t)outsz - 1);
    out[outsz - 1] = 0;
}
```
Семантика: FTP-корень = `/roms`; `CWD /` и `CWD ..` выше корня дают `/roms`; `../..` не выходит. Абсолютные пути клиента трактуются от `/roms` (chroot-поведение). Аутентификация не вводится.

**Дополнительно (низкий риск):** `PWD` (`:226-230`) заменить `strcat` на `snprintf(pr, sizeof pr, "\"%s\"", g_cwd[0] ? g_cwd : "/roms");`.

**Проверка на стенде.**
1. Каталог `/roms/nes` с 50 файлами, имена ≥40 символов. `LIST` 100 раз подряд — UART жив, устройство не падает, ответы 150/226.
2. `CWD /` → `PWD` = `/roms`; `LIST` показывает содержимое `/roms`.
3. `RETR /retro.cfg`, `STOR /x.bin`, `DELE /retro.cfg` → файл вне `/roms` не читается/не создаётся/не удаляется; ответ 550.
4. Штатный сценарий Проводника (вход в папку, скачивание, загрузка) — без изменений.

**Откат:** один файл `net_ftp.c`.

### D2. RX Wi-Fi: единый контракт длины пакета

**Проблема (Critical).** Три независимых места читают за фактической длиной кадра:

- `wifi_net.c:378-381`: если `ip_len > len`, `len` не клампится, и TCP-сумма (`:395-409`) читает `len - ihl` байт;

**Патч A** (`wifi_net.c:378-381`):

**Патч B** (`wifi_net.c:395-397`):

```c
if (tcp_len < 20) return;
```

**Патч C** (`wifi_net.c:430-446`): ограничить окно опций фактическим payload:
```c

if (pay_end > len) pay_end = len;
if (base + 2 > pay_end) return;          /* нет BOOTP+cookie+опций */
for (int oi = 0; base + oi + 1 < pay_end; ) {
    uint8_t c = pkt[base + oi];
    ...
    uint8_t ol = pkt[base + oi + 1];
    if (c == 53 && ol == 1 && base + oi + 2 < pay_end) di_mt = pkt[base + oi + 2];
```

Основной парсер (`:471-492`) уже ограничен `end <= len`; оставить.

**Патч D** (`h3_sdc.c`, join, после вычисления `dp` ~`:5792`):

```c
if (dp + 8 > acc) { off += 24u + drvsz + shift + plen; off = (off + 7u) & ~7u; continue; }
uint32_t avail = acc - (dp + 8);
```

**Патч E** (`h3_sdc.c:6426-6434`): то же самое перед `net_handle_ipv4/arp` (добавить кламп `plen`).

**Проверка на стенде.**
1. Регресс: загрузка, DHCP (OFFER/ACK в UART), FTP-сессия, ping — как до дельты.
2. Инжект (ноутбук в monitor mode + scapy): 1000 кадров 802.11 data с EtherType 0x0800, `ip_len=0xFFFF`, `udp_len=0xFFFF`, порты 67/68, разные `dp` (в т.ч. за `acc`). Ожидание: устройство не падает, UART-лог жив, FTP после инжекта работает.
3. Инжект TCP-сегмента с `off=60`, `len=20` (заведомо битый) — дроп, без зависания.

**Откат:** `wifi_net.c`, `h3_sdc.c`.

### D7. GIC EOI и MMU TEX

**Проблема 1 (High, латентная).** `startup.S:525-535`: `r1` (INTID) не сохраняется через `bl gic_dispatch` (caller-saved) → в `GICC_EOIR` уходит мусор.

**Патч** (`startup.S:531-535`):
```asm
mov r0, r1
push {r1, r2}            @ 8 байт: сохранить INTID и выровнять SP по 8
bl  gic_dispatch
pop {r1, r2}
ldr r0, =0x01C82000
str r1, [r0, #0x10]
```
(пара `r1,r2` сохраняет 8-байтное выравнивание стека при вызове C).

**Проблема 2 (High).** `h3.c:61-65`: `(1u << 16)` — это бит `S`, а не `TEX`; TEX (биты 14:12) вырезан маской, итог — Strongly-Ordered вместо Normal Non-cacheable. Для DMA работает, но противоречит замыслу и запрещает `LDREX/STREX` на `.coherent`.

**Патч** (`h3.c:61-65`):
```c
new_entry = (addr & 0xFFF00000u)
          | (ref & 0x0008DDF0u)   /* NS/AP/nG/domain/XN */
          | (1u << 12)            /* TEX=001: Normal, non-cacheable */
          | (0u << 3) | (0u << 2) /* C=0, B=0 */
          | 0b10u;                /* section */
```
**Важно:** менять только после подтверждения на стенде, что `.coherent` не используется для `LDREX/STREX` (сейчас — нет; `__sync_*` работает по `.bss`).

**Проверка на стенде.**
1. Загрузка, USB-клавиатура, SD, меню — без изменений (D7 меняет атрибут DMA-окна).
2. Временная диагностика (отладочная сборка): после `mmu_mark_uncached` прочитать `((volatile uint32_t*)TTBR0)[0x4A4]` и вывести в UART; ожидание `...0010` (TEX=001, C=0, B=0, S=0).
3. Если звук будет возвращён: включить IRQ, проверить, что INTID 45 приходит один раз и EOI корректен (нет шторма).
4. Стресс: 100 циклов вход/выход из эмуляторов с USB-флешкой (DMA) — без отвала.

**Откат:** `startup.S`, `h3.c`.

### D8. USB / GBA — только верификация (код не меняем)

Находки M1/M2/M5 (USB) и замечания по GBA — **латентные/защитные**, в эксплуатации не воспроизведены. Согласовано: сначала проверка, правка — только при воспроизведении.

**Проверка USB.**

## 4. Почему часть кода не проверена и как это закрыть стендом

Честно: в этом проходе не проверялись построчно:
- `h3_sdc.c` (361 КБ) — SDIO/EHCI/802.11 и WPA 4-way (прочитаны только RX-парсеры и DHCP);
- вендорные ядра (~1.5 млн строк: FBNeo/CPS, Snes9x, FCEUmm, gpSP, fMSX, RACE, Handy, Gearcoleco, ProSystem, atari800) — только host-слои и стыки;
- электрика/тайминги USB, SPI, I2C — без осциллографа;
- динамика (fuzz, нагрузка) — сессия была read-only.

Причины: объём и риск ложных выводов при «сплошном» чтении; эффективнее — точечные статические проходы + стенд-тесты. План закрытия:

| Область | Что проверить | Как |
|---------|---------------|-----|
| `h3_sdc.c` RX/TX | длины дескрипторов, очереди TX, повторы | scapy-инжект + UART-логи; статический проход по `rx_read_packet`, `h3_wifi_tx_data` |
| `h3_sdc.c` SDIO/WPA | 4-way, key install, границы EAPOL | эталон `emulator-refs`/Lakka-дампы; сравнение с rtl8189fs |
| Ядра | парсеры ROM/сейвстейтов (iNES, SNES header, zip) | fuzz-корпус ROM (100 файлов), запуск на стенде |
| USB | BOT/CSW, 4Kn, hot-plug | D8 |
| Тайминги | Sega-пад, тач, SPI | стенд + осциллограф (окно 1.6 мс, 370 кГц) |

## 5. Порядок применения

1. D1 (FTP) — самая опасная и самая локальная; проверить на стенде.
2. D2 (RX) — после D1; сетевой регресс.
3. D3 (TCP peer) — вместе с D2 на одном стенд-прогоне FTP.
4. D4 (аудио-буферы) — независимо, можно параллельно с D5.
5. D5 (FAT) — с образом битой карты.
6. D6 (zip).
7. D7 (GIC/MMU) — последней из кода, т.к. трогает ядро.
8. D8 — верификация.
9. D9 — документация (можно параллельно, но финально — после принятия кода).

После каждой дельты: `make clean && make -j`, загрузка, стенд-тест, `g_fw_version++`, короткая запись в HANDOVER.
