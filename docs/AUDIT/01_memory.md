## A-01 (P1) — сразу за кадром лежат переменные NEOGEO

**r1652:** кадр обёрнут в структуру `g_frame_mem` (0x440A8FA0): кадр 0x3C000
и guard 0x100 — за кадром теперь guard, `nNeoSMARNGAddress` сдвинут на
0x440E50A0. Клампы строк (≤320) в обоих путях рендера уже были, размер
закреплён `_Static_assert`. Ниже — исходная картина (страховка внесена).

`g_frame` заканчивается на 0x440E4F90. Следующий символ — `nNeoSMARNGAddress`
(0x440E4F90), далее `nSMARandomNumber`, `PVCRAM`, `kof10thExtraRAMB`,
`nkof98Protection`, `mslugx_command`, `mslugx_counter` и т.д. — это состояние
NEOGEO-драйвера (`neo_run.cpp`, `d_neogeo.cpp`).

Буфер кадра объявлен как `static uint16_t g_frame[CPS1_W * 320]`
(`cps1_host.cpp:118`), `CPS1_W = 384`, `nBurnPitch = CPS1_W * 2` (`:1106`,
`:1416`). Ёмкость = 384×320 пикселей.

Влияние: **любая** запись за пределы 384×320 (или запись с иным pitch)
попадает в переменные NEOGEO. Это совпадает с формулировкой владельца
«кто-то зацепил её переменные».

Что проверить (требует проверки): список подключённых драйверов с
`BurnDrvGetVisibleSize` шире 384 или выше 320, и все места, где
`pBurnDraw`/`nBurnPitch` переопределяются. Кандидаты-источники: вертикальные
игры (`BDF_ORIENTATION_VERTICAL`) и растровые/широкие наборы; для них
`BurnTransferCopy` пишет `nTransWidth` в строку с pitch 768.

Предложение (после утверждения): проверка `g_frame_w/h` при init с отказом
и логом; страховочный зазор (padding) между кадром и следующими объектами;
перенос NEOGEO-переменных в отдельную секцию.

## A-02 (P1) — исчерпание пула не диагностируется, NULL не проверяется

`burn_memory.cpp:45-75`: `_BurnMalloc` при `s_pool_used + sz > 96 МБ`
вызывает `bprintf(...)` и `return NULL`. Но `bprintf` — **указатель на
заглушку**: `burn.cpp:15` `BurnbprintfFiller(...) { return 0; }`,
`burn.cpp:18` `INT32 (*bprintf)(...) = BurnbprintfFiller;`. В ELF символ
`bprintf` в `.data` (0x416F4BF8), т.е. NULL-вызова нет, но и сообщения нет —
исчерпание пула **молчит**.

Драйверы FBNeo выделяют буферы через `BurnMalloc` и, как правило, не
проверяют NULL (в апстриме это фатально). Значит при нехватке пула идёт
запись по адресу 0 (или рядом) — падение без лога.

Влияние: NEOGEO — самые большие ROM (kof2003/mslug5/svc/garou и т.п.),
поэтому вероятность упереться в 96 МБ максимальна именно у неё.

### Подтверждение арифметикой (r1640)

Суммы `nLen` ROM-таблиц `d_neogeo.cpp` (скрипт по `*RomDesc[]`), МБ:

| Драйвер | Сумма ROM | В driverlist |
|---|---|---|
| cphd | 201,2 | да |
| kf2k1ult | 150,3 | да |
| mslug3x | 148,9 | да |
| kof98ae | 130,6 | да |
| kf2k3pcb | 121,5 | да |
| svcpcb | 112,5 | да |
| badapple | 107,2 | да |
| kof98ult | 91,5 | да |
| kof2003 / kof2003h | 89,5 | да |
| kof96ae | 90,5 | да |

Вывод: **семь включённых сетов физически больше пула 96 МБ** (107–201 МБ) —
на них `_BurnMalloc` гарантированно вернёт NULL, а драйвер пишет по NULL →
падение без сообщения (A-02). Даже 89,5–91,5 МБ впритык: к ROM добавляются
68K RAM, Z80 RAM, VRAM, палитры, буферы спрайтов/тайлов и FM-состояние.

Второй факт: `cps_rgb32` начинается ровно на конце пула (0x5B343900 =
`pool_mem + 96 МБ`) — запаса нет.

Предложение (после утверждения, на выбор):
1. Убрать/пометить из `driverlist.h` сеты > 96 МБ (минимальные правки).
2. Увеличить пул в пределах свободных 0x5B343900..0x5C000000 (≈12,9 МБ) —
   закроет kof98ult/kof2003/kof96ae, но не 100+ МБ.
3. Диагностика: заменить заглушку `bprintf` на реальный вывод при
   `pool exhausted` и возвращать ошибку из `BurnDrvInit` (не падать молча).

### Статус (r1641)

Вариант 2 **утверждён владельцем и выполнен**: `CPS1_MEM_POOL_SIZE` =
106 МБ (`burn_memory.cpp`). Проверено в ELF: `pool_mem` 0x55343900 +

`g_fb` 0x5BE06900..0x5BE83900 — ниже 0x5C000000 (запас ≈1,5 МБ).
`linkcheck: OK`, bin 25 524 236 Б, метка r1641.

Осталось: вариант 3 (реальная диагностика `pool exhausted`) **не утверждён**;
сеты > 106 МБ (`cphd` 201, `kf2k1ult` 150, `mslug3x` 149 и др. в таблицах)

Вариант 1 не требуется, пока в `roms/neogeo` нет сетов > 106 МБ.

## A-03 (P2) — bump-пул не отдаёт память в пределах сессии

`BurnInitMemoryManager()` сбрасывает `s_pool_used = 0` при каждом
`BurnDrvInit` (`burn.cpp:884`). **Закрыто в r1649:** `_BurnFree` откатывает
`s_pool_used`, если освобождаемый блок — последний по адресу
(`ptr + align8(size) == s_pool + s_pool_used`). Этого достаточно для
временных буферов загрузки ROM (`NeoLoadSprites` pBuf1 = 2×C-ROM, буфер
`load.cpp`), которые освобождаются LIFO. Ранние «дыры» по-прежнему не
сжимаются — `BurnRealloc` вверх оставляет старый блок (bump, не free);
проверено на svc: пул вернулся с 110 МБ до 91 МБ, ADPCM-блок 16 МБ влез
в 108 МБ (r1650).

## A-04 (P3) — ZIP-буферы впритык к чужим зонам

`cps1_host.cpp:150-155`: `ZIP_BUF1` = 0x50000000, `ZIP_MAX` = 64 МБ →
конец 0x54000000 = ровно начало `.gbc_bss` (8 МБ); `ZIP_BUF_BIG` =
0x44C00000, `ZIP_MAX_BIG` = 88 МБ → 0x4A400000 = начало `.coherent`;
`ZIP_BUF2` = 0x5C000000, `ZIP_MAX2` = 48 МБ → 0x5F000000.
Запас = 0 байт: любое увеличение лимита или сдвиг зоны даёт перекрытие.
Проверка размера входа есть (`:1057`), но она только отключает zip.

Предложение: уменьшить лимиты на 1 МБ или зафиксировать статическими
assert’ами.

## A-05 (P3) — темп звука не кратен I2S

`nBurnSoundLen` считается драйвером из `nBurnFPS`; для PS3 810 пар/кадр при
59.296 Гц = 48 030 пар/с против 48 000 у I2S. Замер r1637: `drop=0`,
`under` 213–415 за сессию — на текущих данных некритично, но асимметрия
систематическая. Требует проверки на длинных сессиях (накопление).
