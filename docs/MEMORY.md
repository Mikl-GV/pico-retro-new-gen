# MEMORY — карта памяти и правила размещения (актуально r1743)

> Источник истины по адресам: `linker.ld` + `nm/readelf build/h3_bare.elf`.
> Таблицы DRAM для default Musashi пересняты на r1743:
> `.text` = 0x40000000, размер 0xDE3F74; `.rodata` = 0x40DE3F80, 0x5F2388;
> `.data` = 0x413DC650, 0x5425E4; `.bss` = 0x4191F000..0x4479D520
> (0x2E7E520 ≈ 46.5 МБ), `_bstart1`=0x4191F000, `_bend1`=`_hend`=0x4479D520,
> `_coherent_end`=0x4A402A40, `h3_bare.bin` = 26 340 404 Б (r1743, Musashi).
> Cyclone-сборка (`ARC_CYCLONE=1`) больше на ~437 КБ и сдвигает `.text` —
> её адреса сверять `nm` отдельно.
> При изменении состава секций — обновлять этот файл.
> Правила безопасной работы с MMU — `docs/PITFALLS.md`; модель памяти —
> `docs/ARCHITECTURE.md`.

---

## 1. Главный принцип

**В любой момент запущен ровно один эмулятор.** Из этого следует:

- пулы перезанимаются между запусками: `emu_prepare()` сбрасывает
  `gb_heap_reset()` (bump-пул `.gb_heap`) и `newlib_heap_reset()`
  (sbrk-арена); `puae_heap_reset()` — отдельно для Amiga;
- при выходе из эмулятора: `emu_audio_stop()`/`i2s_ring_reset()`, DE2
  возвращается на штатный буфер;
- «зоны разных ядер» могут пересекаться по адресам, потому что simultaneity
  нет (например ROM_BUF и zip-буфер аркад, `.noinit_fbn` и DRAM-пулы).

**Правило:** память берём при запуске, отдаём при выходе; не добавляем
новых «жёстких» секций без `ASSERT` в `linker.ld` и без записи здесь.

### Порт Apple II (POM2, r1388+)

- Кадр Apple II отдаётся как RGBA `uint32_t` (`pom2_h3_pixels`) и пишется
  **напрямую в HDMI-фреймбуфер** (`emu_show_rgba_int` → `fb_draw_addr`), без
  отдельного промежуточного RGB565-буфера POM2. Ниже — только статика порта
  в `.bss`.
- Статика порта в `build/libpom2port.a` тоже уходит в `.bss`: кольцо событий
  `SpeakerDevice` (16 384 × 8 Б = 128 КБ), плюс `s_audio` (4 КБ, `0x44B6F318`
  на r1408) в хосте.
- Объекты машины (`Memory`, `M6502`, `Apple2Display`, `DiskIICard`) — `new`
  из newlib sbrk-арены (`0x4BF00000..0x4EF00000`). `emu_prepare()` в начале
  `emu_run_apple2_pom2()` сбрасывает арену: без него каждый запуск терял
  несколько МБ и на пятом `new Memory()` был data abort (r1391).
- Образ диска: копия 143 360 Б в `DiskImage::loadBuffer` + 35 дорожек по
  6 656 Б (≈233 КБ) nibble-буфера — в той же арене, освобождаются её сбросом.
- Звук — как у всех: пары в кольцо I2S в SRAM A1 (§3), `i2s_push_block`.

## 3. SRAM A1 (0x00000000..0x00006000, без MMU у CPU1/CPU2)

Единственная зона, надёжно видимая всем трём ядрам (CPU1/CPU2 работают с
MMU off). Здесь живут почта, синхронизация и звуковое кольцо.

| Адрес | Назначение |
|---|---|
| `0x18` | one-shot гейт обработчиков исключений (сбрасывается в `_start`) |
| `0x20` | SMP-magic **CPU2** (звук), `0x13579BDF` — писатель `cpu2_entry` |
| `0x24` | статус CPU1 (TFT): `1` — ядро вошло, `0x0E` — прыжок в `tft_core_main`, `2`/`9` — стадия TFT, `0xEF` — вернулись |
| `0x28..0x30` | пробы/диагностика SMP |
| `0x34..0x8C` | SRAM-почта: калибровка тача, кнопки, меню настроек TFT (см. `tft_drv.c`) |
| `0x74` | r162: «игра активна» — core0→CPU1, заморозка TFT-цикла |
| `0x90` | статус CPU2 (audio): `0xA2` — в трамплине |
| `0x94` | SRAM-дубль `g_i2s_ready` (CPU2 видит без MMU) |
| `0x98` | индекс кольца `wr` (продюсер core0) |
| `0x9C` | индекс кольца `rd` (потребитель CPU2) |
| `0xA0` | флаг синхронизации `ring_sync` |
| `0xA4` | `AUDIO_PAUSED` (core0→CPU2: 1 — пауза, FIFO не писать) |
| `0xA8` | `AUDIO_ACTIVE` (core0→CPU2: 1 — идёт игра); CPU2 не читает — диагностика |
| `0xAC` | `AUDIO_FW` (CPU2→core0: пар отдано в FIFO) |
| `0xB0` | `AUDIO_SKIP` (CPU2→core0: срабатываний «FIFO полон») |
| `0xB4` | `AUDIO_BEAT` (CPU2→core0: виток цикла) |
| `0xB8` | `AUDIO_CMD` (core0→CPU2, пауза/резюме) — читает `i2s_audio_poll_cmd` |
| `0xBC` | `AUDIO_ACK` (CPU2→core0: последняя исполненная команда) |
| `0xC0` | стадия CPU2 (`g_cpu2_stage`) |
| `0xC4` | r1727: SMP-magic **CPU1**, `0x13579BDF` — писатель `cpu1_entry` |
| `0x880..0x8A8` | счётчики/дамп исключений (DFAR/LR/DFSR/MPIDR) |
| `0x8B0` | TTBR0 загрузчика, сохранённый startup.S (r1200, диагностика) |
| `0x1000..0x4FFF` | кольцо звука L: 8192 × int16 (16 КБ), r1357 |
| `0x5000..0x8FFF` | кольцо звука R: 8192 × int16 (16 КБ), r1357 |
| `0x9000` | r1683: видео-конвейер — номер задачи `req` (core0→CPU1) |
| `0x9004` | r1683: `done` — номер завершённой задачи (CPU1→core0) |
| `0x9008/0x900C` | r1683: адрес источника (pBurnDraw) / приёмника (`cps_rgb32[n&1]`) |
| `0x9010..0x901C` | r1683: `w`, `h`, страйд источника, флаг поворота 180° |
| `0x9020/0x9024` | r1683: адрес LUT (не используется с r1688) / длительность задачи (мкс) |
| `0x9040..0x9048` | r1685: `TTBR0`/`TTBCR`/`DACR` core0 для MMU вторичных ядер |
| `0x904C` | r1685: фактический SCTLR CPU1 после включения MMU/кэшей |
| `0x9050` | r1685: маска SCTLR для `orr` на CPU1 (с r1688 — `M\|I`, без D-cache) |
| `0x9054` | r1686: SCTLR CPU1 ДО нашей записи (что оставил U-Boot) |
| `0x9058` | r1687: флаг готовности MMU CPU1 (1 = числа в `0x904C/0x9054` валидны) |
| `0x905C` | r1689: счётчик итераций воркер-цикла CPU1 («ядро живо») |
| `0x9060` | r1689: стадия CPU1 (1 = воркер-цикл, 2 = TFT-цикл) |
| `0x9064` | r1689: сколько задач видеоконвейера принял CPU1 |
| `0x9070` | r1716: фактический ACTLR CPU1 (SMP-бит после включения кэшей) |

Почта `0x9000..0x9027` — этап A (видеоконвейер CPU1); **с r1694 конвейер
выключен** (`k_vidw_enable = 0` в `cps1_host.cpp`), почта сохранена под этап B.
Параметры MMU `0x9040..0x9050` — для включения MMU/кэшей на вторичных ядрах
(CPU1 — с r1685; CPU3 — по тому же образцу).

SRAM A1 на H3 — 48 КБ (`0x0000..0xBFFF`): кольцо кончается на `0x9000`,
счётчики/почта лежат ниже `0xC8`, занято: `0x9000..0x9027` — почта
видео-конвейера r1683, `0x9040..0x9070` — параметры MMU и ACTLR r1685/r1716;
запас `0x9028..0x903F` и `0x9074..0xBFFF` свободен (кольцо `0x1000..0x8FFF`
дальше).

**Правило:** новые межъядерные флаги — только сюда (SRAM), не в DRAM:
направление core0→CPU2 через DRAM ненадёжно, а CPU2→core0 не работает вовсе
(история r928/r953 — индексы и кольцо поэтому в SRAM).

**Опыт r1687 (не догма):** строки/структуры через почту передавать пытались —
на практике это ненадёжно, поэтому в коде через почту идут только числа, а
признак готовности читающий ждёт отдельно (как `0x9058` для MMU CPU1; в видео-
и DCS-почте его роль играют номер задачи и порог циклов). Логи печатает то
ядро, которое их пишет. Это выстраданный опыт, а не запрет: при обоснованной
необходимости решение принимает владелец.

**Правило кэшей вторичных ядер (r1688, актуально r1695):** SRAM A1 в таблицах
U-Boot — Normal-память, поэтому D-cache на CPU1/CPU3 включать НЕЛЬЗЯ — почта и
флаги перестают быть видны между ядрами (стенд r1686). Разрешено `SCTLR = M|I`:
I-cache ускоряет выборку, данные идут напрямую, обмен через SRAM работает.
(r1692 пробовал `M|C|I` ради видео-конвейера — откат r1695 за ненадобностью:
конвейер выключен.)

## 4. MMU: LPAE (long descriptors) — как устроено сейчас

Стенд: U-Boot 2025.01 работает в **LPAE** (`TTBCR.EAE=1`,
`TTBCR=0x80000F00`), таблицы 64-битные:

- `TTBR0 = 0x4A40C000` — **L0-копия** (4 КБ, 512 записей × 8 байт);
- записи L0 ссылаются на **L1-копии**: `0x4A410000`, `0x4A411000`,
  `0x4A412000`, `0x4A413000` (по 4 КБ; 2-МБ блоки);
- копии сделаны `startup.S` (r1202) ДО установки стека; оригинальные таблицы
  U-Boot лежат в `0x5FFF1000/0x5FFF2000` и **затираются стеком** — после
  копирования это безопасно;
- `TTBR1` — мусор, не используется (`TTBCR.N=0` — TTBR0 покрывает всё
  VA-пространство; запись L0 в LPAE покрывает 512 ГБ, запись L1 — 1 ГБ).
  **TTBCR/TTBR0/TTBR1 не менять.**

MAIR (снято со стенда):

| MAIR | Значение | Индексы |
|---|---|---|
| `MAIR0` | `0xFFEEAA00` | 0 = Device-nGnRnE (периферия), 1 = `0xAA` (Normal WT), 2 = `0xEE` (Normal WB WA), 3 = `0xFF` (Normal WB WA) |
| `MAIR1` | `0x44E048E0` | 4 = `0xE0`, 5 = `0x48`, 6 = `0xE0`, **7 = `0x44` = Normal Non-cacheable** |

Фактические AttrIndx: **периферия = 0**, **DRAM = 2 (WB)**. Прочие индексы
принадлежат U-Boot — занимать их нельзя (r1203: подмена индекса 4 сломала
USB).

**Что можно/нельзя:**

- `mmu_mark_uncached()` — намеренный **no-op** (r1206): перевод `.coherent`
  в NC ломает OHCI (r1203/r1205). Когерентность держат `cache_clean/
  invalidate` (USB), SRAM-кольцо (r957) и SRAM-индексы (r929);
- любые правки карты — только 64-битными long-дескрипторами; short-формат
  в LPAE-таблицу писать нельзя (r1194-r1201 — не работало вообще);
- `AP[2:1]` в LPAE: `0b01` = RW (EL1+EL0), `0b11` = **RO** (r1202 поймал
  Permission fault на записи в HCCA);
- новые DMA-буферы: класть в `.coherent` (или отдельный регион), но
  **не менять атрибуты** без анализа последствий для OHCI.

## 7. Чек-лист при добавлении нового эмулятора/буфера

1. **Память — из существующих пулов:** `malloc` (`.gb_heap`) или собственный
   bump на sbrk; сброс — в `emu_prepare()`/своём `_reset`.
2. **Новую секцию** — только по образцу `.frodo_bss`/`.a8_bss`: жёсткий VMA,
   `NOLOAD`, `ASSERT` на размер, обнуление в `startup.S`, запись в этот файл.
3. **Не занимать:** `0x5FF00000..0x60000000` (стеки core0), `0x5FBFD000..
   0x5FE01000` (стеки CPU1/CPU2), `0x4A40C000..0x4A420000` (таблицы LPAE),
   `0x4A400000..0x4A402FC0` (DMA-структуры OHCI).
4. **Межъядерная связь** — только SRAM A1; DRAM-флаги ненадёжны.
5. **MMU** — не трогать TTBCR/TTBR; при необходимости атрибутов — сначала
   прочитать MAIR и AttrIndx существующих записей (см. §4) и выбрать
   свободное, затем одна гипотеза = одна прошивка.
6. После изменений — `make clean && make`, обновить этот файл и
   `docs/HANDOVER.md`; при новом «грабле» — запись в `docs/PITFALLS.md`.

## 8. Быстрая сверка (команды)

```bash
arm-none-eabi-readelf -SW build/h3_bare.elf    # размеры/адреса секций
arm-none-eabi-nm build/h3_bare.elf | grep -E "_bstart1|_bend1|_gb_heap|_coherent|_menu_arena|_hend"
```

Эталонные значения r1743 (снято с `arm-none-eabi-nm -S -n build/h3_bare.elf`):
`_bstart1=0x4191F000`, `_bend1=0x4479D520`, `_gb_heap_start=0x4A700000`,
`_gb_heap_end=0x4BF00000`, `_coherent_start=0x4A400000`,
`_coherent_end=0x4A402A40`, `_rgb_hi_end=0x531B8000`, `_menu_arena=0x4F000000`,
`_hend=0x4479D520`.
`pool_mem` (FBNeo) = 0x55343900 (size 0x06C00000, 108 МБ), конец 0x5BF43900;
перед ним (0x54000000..0x55343900) лежат 32-битные кадровые буферы систем.
Имена вшитых BIOS сохранены от PUAE (r1243: сборка UAE4All переиспользует
`puae/kickstart_data.S`; собственной арены/статиков PUAE больше нет);
их адреса в `.data` плавают — брать из `nm` по имени.

Стенд-маркеры (r1204/r1206, норма):
`LPAE[..]: ttbr0=4A40C000 mair0=FFEEAA00 mair1=44E048E0`,
`l0=…4A410003 …4A411003 …4A412003 …4A413003`,
`attr 01C00000=0 40000000=2 4A400000=2 4BF00000=2 5F800000=2`.
