Главные темы:
1. **Мнимое R/W у 7 ядер** компьютерного семейства — ядро считает диск
   записываемым, а `fs_layer` отдаёт `fwrite=0` (тихая потеря данных).
2. **OHCI/EHCI короткий IN не детектируется** (`accepted` всегда `len`) →
   FAT читает мусор из предыдущего приёма.
3. **`sd.c: mmc_write_data`** — единственный путь, где r1271 не применён
   (Data Abort при невыровненном буфере).
4. **`usb_hc_full_recover()` на PHY2** обнуляет interrupt-кольцо
   клавиатуры на этом же PHY — клавиатура «умирает» до перезагрузки.
5. **`cps1_host.cpp:1127`** — `cache_clean(0x9000, 0x80)` задевает
   MMU-строку `0x9040..0x905F` (включая флаг `0x9058`) — отложенный
   false sharing (сейчас конвейер выключен).
6. **Ресемплерные статические буферы** (`rs_phase`, `rs_hist`,
   `s_ring_ema`) не сбрасываются между сессиями — первый кадр новой игры
   стартует со старой фазой.

### 2.1 Межъядерный обмен (класс O / зона 13)

**K-01 · К · `h3_bare/cores/cps1_host.cpp:1127` — `usb_cache_clean(0x9000u,
0x80u)` задевает строку `0x9040..0x905F` (TTBR0, TTBCR, DACR, SCTLR, маска,
факт SCTLR, флаг готовности `0x9058`).**

`cps1_host.cpp:897` и `:930` (r1727) сузили диапазон до `0x28` — правильно.
Но строка `1127` (после `VIDW_REQ = next`) осталась `0x80`, а комментарий
на `:887` («диапазон сужен до 0x9000..0x9028») противоречит строке 1127.
`usb_ohci.c:319-334` округляет `cache_clean` до 32-Б строк: `0x9000..0x907F`
— три линии, третья = `0x9040..0x905F`. Писатель `0x9058` — только CPU1
(`startup.S:897`), читатель `main.c:852-855` (core0). CPU1 пишет флаг
**после включения D-cache** (`startup.S:881-898`), значит строка
разделяемая, и её clean из core0 уносит флаг в DRAM — ровно тот false
sharing, что урок r1726. Сейчас конвейер выключен (`k_vidw_enable=0`),
`0x9058` уже не читается после `main()` — дефект отложенный.

**Доказательство:** grep `0x9058` — только `startup.S:897` (писатель),
`main.c:852-855` (читатель). `cps1_host.cpp:897`/`930` (`0x28`) против
`:1127` (`0x80`).

**Предложение:** заменить 1127 на `usb_cache_clean(0x9000u, 0x28u);`
(как в 930). Комментарий: «чистим ТОЛЬКО почту видео; строка
0x9040..0x905F — MMU-параметры и флаг 0x9058, трогать нельзя». Риск —
минимальный.

**K-02 · К · `h3_bare/cores/i2s.c:129-150` vs `tft_drv.c:191-193` — карта
SRAM A1 не согласована: `0x28/0x2C/0x30` заняты `TFT_PROBE/2/3` (CPU1), но
`docs/MEMORY.md §3` выдаёт их как «пробы/диагностика SMP» без указания
писателя.**

`i2s.c:143` комментирует `0x24..0x8C TFT-почта`, но `0x28..0x30` — вне
`SRAM_AUDIO_*`, и на этом участке живут пробы touch CPU1
(`TFT_PROBE/2/3`). Формально конфликта нет (писатель CPU1 — однократно
при старте, читатель core0 — отладочный), но карта `MEMORY.md` не указывает
писателя — по правилу проекта (зона 13) такой адрес без карты — находка.

**Доказательство:** `tft_drv.c:191-193` — определения `TFT_PROBE*`.
Grep `0x28u|0x2Cu|0x30u` в `h3_bare/` — только `tft_drv.c`.

**Предложение:** дописать в `MEMORY.md §3` строку `0x28/0x2C/0x30` —
писатель CPU1 (`tft_core_main`), читатель core0, ширина u32; в `i2s.c:143`
уточнить диапазон `0x34..0x8C` (не `0x24..`).

**V-03 · В · `h3_bare/cores/cps1_host.cpp:774-776` — перед
`dcs_host_publish()` нет `dsb sy`, хотя порядок `DCS_RUN_TARGET →
DCS_RUN_SEQ → DCS_PING → clean` в модели памяти ARMv7-A не гарантирован.**

`dcs_host_sync` пишет три поля и сразу отправляет clean — это
release-семантика, для которой нужен `dsb sy` **до** clean, иначе CPU1
может увидеть обновлённый `DCS_SEQ` без `DCS_PING`. `usb_ohci.c`
`cache_clean` сам содержит `dsb` только **внутри** PL310-цикла — этого
недостаточно.

**Доказательство:** `cps1_host.cpp:774-777`, `usb_ohci.c:319-334`.

**Предложение:** в начале `dcs_host_publish` добавить
`__asm volatile("dsb sy" ::: "memory");`. Риск — нулевой.

**V-04 · В · `h3_bare/cores/cps1_host.cpp:763-768` — `dcs_host_new_game` не
сбрасывает `DCS_STAMP`/`DCS_TOTAL`/`DCS_STEPS`: `dcs_fail_timeout`
печатает старые `STAMP`/`TOTAL`, что маскирует реальную причину сбоя.**

Stale stamp в `.bss` (DRAM, `0x440EF700`) переживает выход из игры; после
`new_game` и до первого шага worker'а поле содержит старое `0xDC5A0001u`,
и `dcs_fail_timeout` печатает «живое» значение при мёртвом worker'е.
Влияние — только диагностика.

**Предложение:** в `dcs_host_new_game` обнулить `DCS_STAMP`/`DCS_TOTAL`/
`DCS_STEPS` и вызвать `dcs_host_publish()`; в комментарии — «stamp —
индикатор, не флаг готовности».

### 2.3 USB / EHCI / OHCI / SD и буферы (класс J / зона 4)

**U-01 · К · `h3_bare/cores/usb_ohci.c:888-898` — `accepted` всегда `len`
(`td->be` ставит CPU, HC его не пишет), короткий IN не детектируется;
MSD читает мусор из предыдущего приёма.**

Доказательство: `td->be = td->cbp + len - 1` (`:795`); HC обновляет
только `CBP`. `if (cc==0 && accepted != len)` — недостижимо;
комментарий `:894` обещает недостижимую ветку.

**Предложение:** до передачи запомнить `cbp0 = td->cbp`; после — если
`cc==0 && dir_in && td->cbp != cbp0` → `cc = 0x08` (DataUnderrun) →
BOT recovery.

**U-02 · К · `h3_bare/cores/sd.c:168-192` — `mmc_write_data` кастует
`uint8_t*` в `const uint32_t*` и делает LDR с невыровненным адресом =
Data Abort.**

`g_wr.secbuf` (`fat.c:1178`) внутри struct не гарантированно выровнен.
`mmc_read_data` (r1271) уже переведена на `memcpy`, а write — нет (ровно
тот же D-22 не применён к write-пути).

**Предложение:** `uint32_t w; memcpy(&w, buf + (i<<2), 4); MMC->fifo = w;`.
Риск — нулевой.

**U-03 · К · `h3_bare/cores/usb_ohci.c:778-810` — `memset(&g_bulk_td, 0,
...)` после таймаута `bulkcur` (до 20 мс) без принудительного
`bulk_release`; HC может читать TD во время затирания.**

**Предложение:** при `bulkcur != 0` после цикла — `bulk_release()` и
`-1`.

**U-04 · К · `h3_bare/cores/usb_msd.c:114-121` — `CSW.residue` не

**U-05 · К · `h3_bare/cores/usb_hc.c:326-334` — `usb_hc_full_recover()` на

**U-06 · К · `h3_bare/cores/usb_ohci.c:103` — `g_mps` глобальный на два

## 4. Узкие места hot-path (оптимизации до NEON/ASM)

- **`i2s_poll_fill`** (`i2s.c:585-697`) — CPU2, до 24 пар за вызов,
  `dmb` перед чтением `rd`, `dsb` не нужен (SPSC). Чтение `ring_l()[idx]`
  / `ring_r()[idx]` — скалярно, 2×int16 = 4 байта из SRAM. NEON не
  поможет: чтение из SRAM (не D-cache) быстрее любой перестановки.
- **`cps_row_rgb32`** (`cps1_host.cpp:983-1001`) — уже NEON, 8 px за
  итерацию (r1684); формула совпадает с LUT. Остающийся скалярный
  хвост — `w % 8` пикселей. Для 384×256 это ~0.04 мс/кадр — выигрыш
  пренебрежим.
- **`usb_cache_clean`/`invalidate`** (`usb_ohci.c:319-334`) — DCCMVAC
  построчно + PL310 `CLEAN_INV_PA`; при частых вызовах (DCS, почта)
  накладные расходы заметны на длинных диапазонах. Оптимально —
  `dc civac` (by set/way) только при смене контекста, точечные — как есть.
- **`resampler44`** (`resampler44.c:116-193`) — 8 тапов × 64 фазы,
  `int64`-аккумулятор, ~2 умножения на тап. На `VFP/NEON` можно
  выиграть ~1.8×, но риск смены округления; для 800 пар/кадр выигрыш
  ~0.1 мс — не стоит.
- **`emu_scale`/`emu_scale_int`** (`emu.c`) — ближайший кандидат на NEON,
  но вне задачи этого аудита (см. `docs/ARCHITECTURE.md`,
  «Производительность»).

на 0x54000000; но если `.bss` вырастет и упрётся в 0x54000000 — `ASSERT` на
`.fs_bss`/`.frodo_bss`/`.rgb_hi` сработает раньше. Сейчас рост `.bss` = 46.5 МБ

## 8. Что не проверено и почему

1. **Стенд:** никакие правки не проверялись на железе — вели бы их
   отдельно. Все «К» и «В» — по коду.
2. **`emulator-refs`** — у USB нет EHCI/OHCI-драйверов U-Boot для сверки
   (только clk/dma/pinctrl); сверял по памяти с EHCI USB 2.0 и OHCI 1.0a
   и Linux `ohci-hcd`/`ehci-hcd` (по семантике `RH_PS_*`, HCCA, TD-CC).
   По SD — `h3_sdc.h` (вендор H3), по CHS/INT13h — RBIL.
3. **Реальные адреса `.coherent`-объектов**: `nm -S` показывает только
   границы секции (0x4A400000..0x4A402A40); конкретный порядок
   `g_bulk_td`/`g_int_td`/`g_hcca` — по порядку объявления; соседство в
   пределах строки 32 Б для `g_kbd`/`g_touch`/`g_pad` — **требует
   `nm -S build/h3_bare.elf | sort | grep g_`** (не запускал отдельно).
4. **USB-MSD 4Kn** — `usb_msd_read_capacity` не проверен: если U-Boot/этот
   стенд отдаёт 4Kn-флешку, U-07 будет срабатывать даже без recover
   (первое подключение). На стенде флешка, скорее всего, 512b, но код
   не защищён.
5. **Полная разметка `.coherent` по `nm`** для проверки U-08 (соседство
   `g_touch≥g_kbd+32`) — не сделана.
6. **F12 в POM2/Агат/WOZ** — только по коду `disk_swap.c:253`/`245`; на
   стенде не вставлял WOZ размером >1 МБ.
7. **Прогон длительной сессии** (перезаход 50+ раз) — не выполнялся; L-02
   (фаза между сессиями) выявляется именно стендом.
8. **PXT-звук** — `pxt_host.c:531` требует явной сверки частоты и ресемплера;
   в таблице §7 указан «44100?» — по коду не подтвердил.
9. **CPS 032bpp буферы (`cps_rgb32` в `.rgb_hi`) — в реальном `ASSERT`**:
   `_rgb_hi_end = 0x531B8000` (readelf), пока 0x53E00000 — запас 2.2 МБ,
   рост W/H конверсии (до 400×320 = 512 КБ) — влезет.
10. **`.ep_bss`** — на 0 байт; реальные объекты EP (буфер 884 КБ) — надо
    найти в `nm`: если в общем `.bss` — M-01 становится серьёзным (документ
    лжёт, не только формальность).
