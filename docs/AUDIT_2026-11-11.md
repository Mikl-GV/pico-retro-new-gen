## 2. НАХОДКИ

### Слой 1. Platform

**P1-В-ЗАКРЫТО. PLL_AUDIO: SDM-паттерн и делители из РАЗНЫХ строк таблицы linux**
`h3_bare/cores/i2s.c:267-268`:
```c
PLL_AUDIO_PAT  = 0xc000ac02u;
PLL_AUDIO_CTRL = 0x80035514u;   /* EN=1, N=86, M=21, P=4 → 24.571 МГц */
```
- Суть: `0xc000ac02` — SDM-паттерн из таблицы `ccu-sun8i-h3.c`
  (`sdm_table`), который в linux задаётся ПАРОЙ с делителями **N=14, M=14**
  для 24.576 МГц (вторая строка — `{0xc0010d84, 8, 7}` для 22.5792 МГц).
  Здесь же делители N=86, M=21, P=4 → 24.571 МГц (другая частота, в linux
  как штатная не используется). SDM-модулятор настроен на спрэд, рассчитанный
  для другой пары делителей.
- Почему важно: PLL выдаёт не чистые 24.571 МГц — SDM добавляет
  дробно-дельта-модуляцию по паттерну 24.576 МГц; итоговая тактовая и
  фактический LRCK отличаются от расчёта (i2s.c:1104 считает ровно
  24 571 000). На звук влияет слабо (спрэд в пределах ppm), но это прямое
  расхождение код ↔ референс-код ядра H3.
- Доказательство: `ccu-sun8i-h3.c`
  `pll_audio_sdm_table[...] = { {22.5792MHz, 0xc0010d84, 8, 7}, {24.576MHz, 0xc000ac02, 14, 14} }`.
  Наш код берёт паттерн из строки 24.576, а делители — произвольные.
- Предложение: либо писать `PLL_AUDIO_PAT = 0` (SDM off), оставив делители
  86/21/4 (простая, предсказуемая 24.571 МГц), либо поставить пару из
  таблицы на 24.576 МГц (N=14, M=14; проверка P по даташиту). Минимальный
  риск регрессии (меняет только тактовую PLL), требует стенд-проверки
  отсутствия дропа и «щелчков».

**P2-С. docs↔ELF: «эталонные» адреса в MEMORY.md §8 и PITFALLS.md устарели**
- `docs/MEMORY.md:214-217` «Эталонные значения r1241»
  `_bstart1=0x420F5000`, `_bend1=0x490AD850` НЕ совпадают с таблицей §2
  (стр. 36: `0x421D1000..0x49189850`) и с фактом (`nm`):
  `_bstart1=0x421D1000`, `_bend1=0x49189850`, `_hend=0x5A000000`,
  `_gb_heap_start/end=0x4A700000/0x4BF00000`, `_coherent_*=0x4A400000/
  0x4A402FC0`, `_menu_arena=0x4F000000`. Внутреннее противоречие одного
  документа.
- `docs/PITFALLS.md:97-98` (и §6, стр. 120): `.noinit_fbn 0x431D3418`,
  `.bss (0x420B5000..0x4906D850)` — устарели: фактически пул FBNeo
  закреплён на `0x54000000` (linker.ld r1191), BSS — `0x421D1000..`.
  Могут сбить с толку при новых ядрах.
- Предложение: пересчитать эталон `nm`-ом после следующей сборки, обновить
  оба файла; риск нулевой (документация).

**P3-Н. TFT_PROBE3 «PC3 контроль» — фактически проба CS дисплея**
`h3_bare/cores/tft_drv.c:193` — комментарий «PC3 контроль», а
`tft_core_main` (стр. 1172) делает `tft_touch_probe_cs(0, 0x90)` — то есть
пробует тач через CS **дисплея** (sel=0). Формально это диагностическая
проба «гонки по шине», но подпись вводит в заблуждение. Н (косметика).

**P4-К. Amiga/PUAE: тёплый вход r1241 больше не возвращает память арены —
рост ~15 МБ/вход, `rtarea exhausted` на ~4-м входе** — **ЗАКРЫТО r1243
(полная замена PUAE → UAE4All)**
- Симптом (стенд-лог владельца, 2026-11-11): три входа дают
  `Amiga heap: base=4BF00000 brk=4C80B300 → 4D70E120 → 4E5F8F30`, чётвёртый —
  `virtual memory exhausted (rtarea)!` + `Internal error; autoconf.c:580` +
  `PANIC`. Начинается у 0x4EF00000 (`SBRK_LIMIT`, libc_min.c:334), 48 МБ sbrk.
- Причина (код): `puae_host.c:614` `g_warm = (g_core_inited && gen==…)` —
  при тёплом входе **не вызывается `puae_heap_reset()`** (только в cold-ветке
  615-626), а free-list не сжимает хвост между сессиями (пуае_free отдаёт
  tail только **внутри** текущей арены, puae_host.c:531-548). Ядро держит
  статики (chipmem/богамem/prefs) между unload/load; r1235 лечил холодным
  входом + прокруткой слотов, **r1241 вернул тёплый вход — рост возобновился**.
- Доказательство: рост brk из лога; отсутствие `puae_heap_reset()` в тёплой
  ветке (код); `SBRK_LIMIT`. Повторяемость: каждый тёплый вход, на 4-6.
- Предложение (см. план Д7): сжимать арену при тёплом входе
  (`puae_heap_trim()`: вернуть свободный хвост через brk) ИЛИ делать полный
  холодный цикл каждый 2-й вход (как r1235 — проверено на стенде). Риск:
  низкий (не трогает `_sbrk` контракт, `emu.c`, интерфейсы).
- **Статус r1243: PUAE удалён из сборки, ядро заменено на UAE4All (Cyclone,
  холодный init на каждый вход, sbrk-арена PUAE не используется). Архитектурно
  закрывает рост арены и `rtarea exhausted`.**

### Слой 3. Драйверы

**D1-В-ЗАКРЫТО. Диагностика I2S считает 24.571 МГц, баннер печатает 24.576**
`h3_bare/cores/i2s.c:1104` (`uint32_t pll = 24571000u;` — расчёт LRCK) и
`i2s.c:1148` (`"I2S: ready (48k stereo, PLL 24.576M)"`, шапка файла —
24.576 МГц). Код устанавливает 24.571 (см. P1). Лог при включённом
диагностическом выводе внутренне противоречив; пользователь видит
«24.576M» при фактической 24.571 МГц. В (дезинформация при отладке).
Предложение: свести к одному значению (24.571 МГц) в шапке/баннере/DIAG;
риск нулевой. **Статус: по указанию владельца («1 — не лезь, там всё ОК,
5 — не критично») — ЗАКРЫТО, исправление не требуется.**

**D2-В-ЗАКРЫТО. SD-буфер `g_sec[512]` в обычном `.bss` без кэш-обработки**
`h3_bare/cores/sd.c:67` (`static uint8_t g_sec[512];`) — читается
`mmc_read_data(g_sec, 512)` (sd.c:140). Проверено по коду (sd.c:104-129,
167-191): MMC работает **только через FIFO-регистры и STATUS-поллинг —
это PIO, DMA не используется** (ни `dmac`/`dlba`-регистры, ни
`RINT_DMA_*`). Значит `g_sec` в обычном `.bss` безопасен, кэш-обработка
не нужна. **Статус: ЗАКРЫТО, изменений не требуется.**

**D3-С. TFT: обновление меню по эпохе — флаш 44 строк на 8 МГц SPI**
`h3_bare/cores/tft_drv.c:846-848`: при `full=0` (смена только эпохи —
например, F1) рендерится `tft_flush_rect(0, 116, TFT_W, 44)`. Это
480×44 пикс × 2 байта ≈ 42 КБ через по-байтовый SPI на 8 МГц с лэтчем
CS на каждый пиксель — десятки мс. Для редкого события (нажатие F1) —
терпимо, но на слабом стенде заметно. С. Предложение: сузить до строки
динамического текста (diff-область) или батчить по 16-битным словам
(`tft_flush` уже по словам, а rect — по-байтовый путь, `tft_flush_rect`).
Риск: UI-регрессии, требует аккуратного diff.
